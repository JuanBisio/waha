# Revisión de seguridad — Turnero SaaS

**Fecha:** 2026-09-02
**Alcance:** `turnero-saas` en revisión `70eb122` — rutas API, lógica de WhatsApp/IA, widget, middleware y las 78 migraciones SQL.
**Método:** lectura manual dirigida a la superficie de ataque. **No** es el escaneo multi-agente del plugin `claude-security` (no estaba disponible); no hubo panel de verificación de tres votos, así que cada hallazgo lleva abajo cómo comprobarlo.

> **Advertencia sobre el estado real de la base.** Muchas migraciones no siguen la convención `<timestamp>_nombre.sql` y varias son claramente scripts sueltos (`inspect_data.sql`, `check_demo_data.sql`, `diagnose_one_slot.sql`). No se puede saber desde el repo cuáles se aplicaron realmente ni en qué orden. El análisis de abajo asume el orden lexicográfico que usa `supabase db push`. **Hay que verificarlo contra la base viva antes de dar nada por cierto.**

Los seis críticos comparten una misma raíz: **la `anon key` de Supabase se trata como si fuera secreta.** No lo es — se publica en el bundle del navegador de cada visitante del widget, y además está versionada en `workflows/*.json`. Todo lo que quede accesible al rol `anon` es público.

## CRÍTICO

### C1 — `/api/v1/whatsapp/outbound` no tiene autenticación

[src/app/api/v1/whatsapp/outbound/route.ts](turnero-saas/src/app/api/v1/whatsapp/outbound/route.ts) — el handler completo, no hay ni `auth.getUser()` ni API key ni verificación de shop. El `matcher` del middleware excluye `api/v1/whatsapp`, así que tampoco pasa por ahí.

Cualquiera en internet puede hacer:

```
POST /api/v1/whatsapp/outbound
{"contact_id":"<uuid>","recipient":"+54...","message":"texto arbitrario"}
```

y el servidor envía ese WhatsApp **desde el número verificado del negocio**, con la API key por defecto de YCloud.

**Impacto:** phishing con la identidad de marca del cliente, spam a costa del negocio, y baneo casi seguro del número de WhatsApp Business. Además ensucia la bandeja vía `handle_outbound_message` con un `contact_id` elegido por el atacante.

**Cómo comprobarlo:** un `curl` contra el endpoint en producción sin ninguna credencial.

**Arreglo:** exigir sesión autenticada + verificar que el usuario pertenece al shop dueño de `contact_id`. Es el mismo patrón que ya usa [webhooks/test/route.ts](turnero-saas/src/app/api/v1/admin/webhooks/test/route.ts), que sí está bien hecho.

### C2 — `anon` puede leer las credenciales de todos los negocios

[supabase/migrations/999_fix_rls_and_security.sql:169](turnero-saas/supabase/migrations/999_fix_rls_and_security.sql#L169)

```sql
CREATE POLICY "Public shops access"
  ON shops FOR SELECT
  TO anon
  USING (true);
```

La tabla `shops` guarda secretos por tenant — confirmado en [20260504_multitenant_whatsapp.sql:7-9](turnero-saas/supabase/migrations/20260504_multitenant_whatsapp.sql#L7-L9):

- `ycloud_api_key` — API key de YCloud del negocio
- `ycloud_webhook_secret` — secreto HMAC del webhook
- `api_key_n8n` — la key que autentica `/api/v1/admin/appointments/external`
- `webhook_url`

Con la anon key (pública) se hace `select * from shops` y salen todas, de todos los tenants.

**Impacto:** exfiltración total de credenciales. Con `api_key_n8n` se crean turnos en cualquier negocio; con `ycloud_api_key` se manda WhatsApp desde cualquier número; con `ycloud_webhook_secret` se firman webhooks falsos válidos.

**Arreglo:** mover los secretos a una tabla aparte sin acceso `anon`, o restringir columnas con una vista. Una policy de SELECT no puede limitar columnas — hay que separar la tabla.

### C3 — `anon` puede leer todos los turnos de la plataforma

[supabase/migrations/999_fix_rls_and_security.sql:128](turnero-saas/supabase/migrations/999_fix_rls_and_security.sql#L128)

```sql
CREATE POLICY "Public users can view appointments"
  ON appointments FOR SELECT
  TO anon
  USING (true);
```

Devuelve `customer_name`, `customer_phone`, `customer_email`, `start_time` y `cancellation_token` de **todos los turnos de todos los negocios**.

**Impacto:** volcado completo de PII de clientes. Y como incluye `cancellation_token`, encadena con C5.

**Nota sobre el orden de migraciones:** [20260131_fix_security_critical.sql](turnero-saas/supabase/migrations/20260131_fix_security_critical.sql) hace bien este trabajo — restringe el SELECT de `appointments` al staff. Pero `999_...` ordena **después** de `20260131_...` en orden lexicográfico (`'2' < '9'`), así que lo pisa. La migración que se llama "fix_security_critical" queda anulada por otra que corre después.

### C4 — `webhook_logs` es de lectura pública

[supabase/migrations/enable_log_access.sql:2-6](turnero-saas/supabase/migrations/enable_log_access.sql#L2-L6)

```sql
CREATE POLICY "Public read access" ON public.webhook_logs FOR SELECT USING (true);
GRANT SELECT ON public.webhook_logs TO anon;
```

El comentario dice "for debugging". Los archivos sin prefijo numérico ordenan **al final**, así que esto se aplica después de todo lo demás.

La columna `payload` guarda el webhook entero: nombre, teléfono, email del cliente, datos del turno y el `cancellation_token`.

**Arreglo:** borrar la policy y el grant. Esto era temporal y quedó.

### C5 — `cancel_appointment` no verifica propiedad

[supabase/migrations/add_cancellation_rpc.sql:30](turnero-saas/supabase/migrations/add_cancellation_rpc.sql#L30)

```sql
CREATE OR REPLACE FUNCTION cancel_appointment(p_appointment_id uuid)
RETURNS json AS $$
BEGIN
  UPDATE appointments SET status = 'cancelado'
  WHERE id = p_appointment_id::uuid
  ...
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

`SECURITY DEFINER`, sin `SET search_path`, y **sin una sola comprobación de quién pide la cancelación**. En Postgres `CREATE FUNCTION` otorga `EXECUTE` a `PUBLIC` por defecto, así que queda expuesta vía PostgREST al rol `anon`.

Dos caminos de explotación:

1. **Directo:** con la anon key, `rpc('cancel_appointment', {p_appointment_id: '<uuid>'})` cancela cualquier turno. Los UUID salen de C3 o C4.
2. **Vía el bot:** en [inbound/[shop_slug]/route.ts](turnero-saas/src/app/api/v1/whatsapp/inbound/[shop_slug]/route.ts), cuando la sesión está en `AWAITING_CANCEL_SELECTION` y el usuario manda un UUID, se llama a `handleCancellation` → `cancel_appointment` con el service role y sin verificar que el turno sea de ese teléfono ni de ese shop. Nada obliga a que el UUID sea uno de los de la lista que se le mostró.

**Impacto:** cancelación masiva de la agenda de todos los negocios.

**Arreglo:** agregar `p_customer_phone` (o `p_shop_id`) y filtrar por él en el `UPDATE`; revocar `EXECUTE` a `anon`/`public`.

### C6 — La verificación de firma HMAC falla en abierto

[src/lib/whatsapp/signatureVerifier.ts:13-15](turnero-saas/src/lib/whatsapp/signatureVerifier.ts#L13-L15)

```ts
if (!secret || secret.includes("TODO")) {
  console.warn("[Signature] YCLOUD_WEBHOOK_SECRET no configurado. Saltando verificación.");
  return true;
}
```

Si el secreto no está configurado (o contiene "TODO"), **la función devuelve `true`**: firma válida. No es un caso teórico — en [inbound/[shop_slug]/route.ts](turnero-saas/src/app/api/v1/whatsapp/inbound/[shop_slug]/route.ts) el secreto sale de `shop.ycloud_webhook_secret ?? process.env.YCLOUD_WEBHOOK_SECRET ?? ""`, y esa columna es `NULL` para cualquier shop que no la haya cargado. Un tenant sin configurar tiene el webhook completamente abierto.

Peor: el log del llamante dice `"Firma inválida rechazada o Secreto no configurado"` — pero cuando el secreto no está configurado **no rechaza**, deja pasar.

Con el webhook abierto, un atacante inyecta eventos de WhatsApp falsos que se procesan con el **service role key**: reservar, cancelar, escribir en la bandeja, y gastar mensajes salientes.

**Arreglo:** invertir la condición — sin secreto, `return false`. Que un tenant mal configurado no reciba mensajes es un fallo visible y corregible; que los reciba de cualquiera, no.

## ALTO

### A1 — El CAPTCHA de Turnstile no se verifica en el servidor

[src/components/widget/steps/Step5CustomerForm.tsx:46](turnero-saas/src/components/widget/steps/Step5CustomerForm.tsx#L46) hace `if (!state.captchaToken)` en el navegador — y el token **nunca se envía**: el `body` del `fetch` a `/api/public/appointments` (líneas 89-103) no lo incluye, y [public/appointments/route.ts](turnero-saas/src/app/api/public/appointments/route.ts) nunca lo valida contra Cloudflare.

El CLAUDE.md dice "CAPTCHA: Cloudflare Turnstile en el widget público". En la práctica es decorativo: se saltea llamando la API directo.

**Arreglo:** mandar el token en el body y validarlo server-side contra `https://challenges.cloudflare.com/turnstile/v0/siteverify` antes de insertar.

### A2 — `/api/v1/webhooks/trigger` no tiene autenticación

[src/app/api/v1/webhooks/trigger/route.ts:14](turnero-saas/src/app/api/v1/webhooks/trigger/route.ts#L14) — acepta `{appointmentId}` de cualquiera y dispara `sendAppointmentConfirmation` (WhatsApp o email, **pago**) más el webhook del shop.

No hace falta adivinar UUIDs: el widget devuelve `result.data.id` a quien reserva. Se reserva una vez y después se martilla el endpoint con ese id.

**Impacto:** consumo ilimitado de créditos de YCloud, spam al cliente, y amplificación de tráfico contra el `webhook_url` de terceros.

**Arreglo:** que el trigger salga del servidor dentro de `/api/public/appointments` en vez de ser un endpoint llamable desde el navegador.

### A3 — SSRF por `webhook_url` sin validar

[src/lib/webhooks/webhookUtils.ts:188](turnero-saas/src/lib/webhooks/webhookUtils.ts#L188) — `fetch(webhookUrl, {...})` sin ninguna comprobación: ni esquema, ni bloqueo de IP privadas/link-local, ni límite de redirecciones.

`shop.webhook_url` lo define el dueño del shop desde el dashboard, y cualquiera que se registre puede crear uno. Se dispara a demanda desde `/api/v1/admin/webhooks/test`.

Es SSRF a ciegas (solo vuelve el status code, no el cuerpo), pero permite alcanzar servicios internos y hacer POST contra ellos, y el status + timing filtran información.

**Arreglo:** exigir `https:`, resolver el host y rechazar rangos privados/loopback/link-local, `redirect: 'manual'`.

### A4 — El `cancellation_token` lo genera el cliente

[Step5CustomerForm.tsx:82](turnero-saas/src/components/widget/steps/Step5CustomerForm.tsx#L82) genera el token en el navegador y lo manda en el body; [public/appointments/route.ts](turnero-saas/src/app/api/public/appointments/route.ts) lo inserta tal cual.

La entropía actual está bien (`crypto.getRandomValues`, 128 bits), pero es un token de seguridad bajo control del cliente: nada impide mandar un valor fijo, ni repetir el mismo token en muchas reservas (lo que rompe el `.single()` de la ruta de cancelación).

El servidor ya tiene `generateCancellationToken()` para esto y lo usa en la ruta `external`. La ruta pública debería hacer lo mismo.

### A5 — `/api/public/appointments` no valida el turno

[public/appointments/route.ts](turnero-saas/src/app/api/public/appointments/route.ts) valida que `service_id` pertenezca a `shop_id` — pero:

- **no valida `professional_id` contra `shop_id`** (el comentario dice "Defense in Depth" pero solo cubre el servicio);
- **no valida `start_time`/`end_time` contra nada**: vienen del cliente y se insertan. Se puede reservar fuera de horario, en el pasado, o con una duración que no corresponde al servicio.

La única protección real es el constraint de exclusión `appointments_no_overlap`, que evita superposiciones pero no horarios inválidos.

### A6 — `GRANT ALL ON booking_sessions TO anon`

[20260209_add_session_state.sql:27](turnero-saas/supabase/migrations/20260209_add_session_state.sql#L27) — `anon` puede leer, modificar y borrar cualquier sesión de conversación. Con las RPC de sesión también otorgadas a `anon` (líneas 117-119), se puede manipular el estado de la conversación de otro usuario del bot.

También `GRANT EXECUTE ON FUNCTION book_appointment_by_name(...) TO anon` ([fix_booking_timezone.sql:67](turnero-saas/supabase/migrations/fix_booking_timezone.sql#L67)) permite reservar salteándose la API entera.

## MEDIO

- **M1 — Comparación de firma no constant-time.** [signatureVerifier.ts:38](turnero-saas/src/lib/whatsapp/signatureVerifier.ts#L38): `receivedSig === expectedSig`, con el comentario "Comparación robusta". Usar `crypto.timingSafeEqual`.
- **M2 — Sin validación de timestamp en la firma.** El `t=` se parsea y se usa para armar el payload, pero nunca se compara contra la hora actual. Un request firmado capturado se puede reproducir para siempre.
- **M3 — `get_client_appointments` no filtra por shop.** [add_cancellation_rpc.sql](turnero-saas/supabase/migrations/add_cancellation_rpc.sql) filtra solo por `customer_phone`: un cliente que escribe al bot del negocio A ve sus turnos de todos los negocios. Además es `SECURITY DEFINER` y alcanzable por `anon` con cualquier teléfono.
- **M4 — `p_shop_slug: "demo"` hardcodeado.** [inbound/route.ts:47](turnero-saas/src/app/api/v1/whatsapp/inbound/route.ts#L47) — todos los mensajes entrantes de esta ruta legacy se atribuyen al shop "demo". Sigue viva y sin auth. Si ya no se usa, borrarla.
- **M5 — 17 archivos definen funciones `SECURITY DEFINER` sin `SET search_path`.** Vector conocido de escalación por secuestro de `search_path`; el linter de Supabase lo marca como `function_search_path_mutable`. Solo 9 de 26 archivos lo fijan.
- **M6 — Fuga de errores internos.** [inbound/route.ts](turnero-saas/src/app/api/v1/whatsapp/inbound/route.ts) devuelve `details: error.message` de la base; [availability/route.ts](turnero-saas/src/app/api/v1/availability/route.ts) devuelve `error.message` crudo; `bookAndRespond` manda el texto del error de Postgres por WhatsApp al cliente.
- **M7 — La anon key está versionada.** En los 10 `turnero-saas/workflows/whatsapp_bot_*.json` (commit `cdd12d8`), junto con el project ref `nyoodvdlrrkgibjbxmgj`. La anon key es pública por diseño, así que **no es un leak en sí** — pero le entrega al atacante exactamente la llave que abre C2, C3, C4 y C5. No hay ninguna `service_role` versionada (verificado).
- **M8 — `/api/v1/availability` no tiene auth** pese a que el CLAUDE.md la documenta como "Con auth". Es un duplicado sin protección de la ruta pública.
- **M9 — Chequeo de colisión roto en la ruta `external`.** [external/route.ts](turnero-saas/src/app/api/v1/admin/appointments/external/route.ts) paso 8: busca turnos con `start_time >= inicio AND start_time < fin`. Un turno que empieza **antes** y termina **después** del inicio nuevo no se detecta. El constraint de exclusión lo ataja en la base, pero devuelve un 500 en vez de un 409 limpio. El rate limit en memoria (`rateLimitStore`) además no sirve en serverless: cada instancia tiene el suyo.

## Lo que está bien

Vale decirlo, para no perderlo en un refactor:

- [admin/webhooks/test/route.ts](turnero-saas/src/app/api/v1/admin/webhooks/test/route.ts) hace la verificación completa: sesión + rol `owner`/`admin` en el shop. Es el patrón a copiar en las rutas de C1 y A2.
- Las RPC de reserva y disponibilidad usan plpgsql parametrizado — **no hay inyección SQL** en `book_appointment_by_name` ni en `get_available_slots` (verificado: los `EXECUTE` que aparecen son todos `GRANT EXECUTE`).
- El middleware usa `supabase.auth.getUser()` contra el servidor, no confía en la cookie.
- El constraint `appointments_no_overlap` da una defensa real en la base contra doble reserva.
- No hay `service_role` key versionada, y `.env*` está correctamente en `.gitignore`.

## Orden sugerido

1. **C1** — autenticar `/whatsapp/outbound`. Es el más fácil de explotar y el que más daño reputacional hace.
2. **C2, C3, C4** — las tres policies `USING (true)`. Un solo archivo de migración las arregla.
3. **C6** — invertir el fail-open de la firma. Tres líneas.
4. **C5** — ownership en `cancel_appointment` + revocar el grant.
5. **A1, A2, A4** — el ciclo de reserva del widget.
6. El resto.

Antes de arrancar conviene resolver el desorden de migraciones: renombrar todo a `<timestamp>_nombre.sql`, sacar los scripts de diagnóstico de `migrations/`, y confirmar contra la base viva qué policies están realmente activas. Mientras el orden de aplicación sea ambiguo, cualquier arreglo puede quedar pisado por un archivo que ordena después — que es exactamente lo que le pasó a `20260131_fix_security_critical.sql`.

## Acción requerida antes de desplegar

1. **`TURNSTILE_SECRET_KEY`** — sin esta variable, `/api/public/appointments` responde 503 y no se puede reservar. Es deliberado: un CAPTCHA que se saltea al faltar configuración no es un CAPTCHA.
2. **`ycloud_webhook_secret`** por shop (o `YCLOUD_WEBHOOK_SECRET` global) — con la firma fallando cerrado, un shop sin secreto deja de recibir mensajes.
3. **Rotar credenciales.** Mientras la policy `"Public shops access"` estuvo activa, cualquiera con la anon key podía leer `ycloud_api_key`, `api_key_n8n`, `webhook_secret` y `mp_access_token` de todos los negocios. Hay que asumirlas comprometidas y regenerarlas.
